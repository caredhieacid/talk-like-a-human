# 防御性写法：怎么认出来，怎么改

防御性的话是写的人为了“万一错了不怪我”加上去的。读的人从里面得不到能用的信息，还要多读几句；满篇提醒和“可能”，反而分不清哪一句是真要紧的。

这份文件不用每次都读。改写、审阅别人的文字，或者拿不准某句提醒该不该留时，再来查。

## 怎么判断

每句提醒、限定、免责，先问：删掉它，读者会少知道什么，或者更容易做错什么吗？拿不准时，再细问三个问题：谁会用到这句话？它改变了读者的什么理解或决定？删掉它，哪句话会变得不对？三个都答不上来，就是防御性的话。

然后从四种处理里选一种：

| 什么样的句子 | 怎么处理 |
| --- | --- |
| 只为显得尽职、预防批评；声明自己“并不是要说……”；没做错时的道歉 | 整句删掉 |
| 确实不确定，但“可能”“一定程度上”叠了好几层 | 只留一层，说清不确定来自哪里 |
| 限定堆在开头、结尾或脚注，离它限定的那句话很远 | 挪到那句话旁边 |
| 影响意思、证据强弱、适用范围，或涉及安全、钱、健康、法律、合同 | 留下，写具体，只写一次 |

不要按关键词判断。同一个“可能”，在“这个改动可能让旧版客户端无法登录”里是要紧的风险，在“这可能是一个值得考虑的方向”里是多余的保险。

## 常见的十种

每种先列中文和英文的典型说法，再说怎么改。这些是例子，不是禁用词表；看它在句子里有没有用。

### 1. 笼统免责

- 以上内容仅供参考 / 不构成专业建议 / 具体请咨询专业人士 / 请以实际情况为准 / 作为 AI，我无法……
- This is not professional advice. / Consult a professional. / As an AI, I can't… / Results may vary.

改法：删掉。真有需要找医生、律师、会计的情况，说清什么情况下找谁。真有和这件事有关的能力限制，具体说出来：“我打不开这个链接，所以下面是按你贴的内容写的。”

- ❌ 以上内容仅供参考，具体请咨询律师。
- ✅ 劳动合同签三年以上的，试用期最长六个月；签一到三年的，最长两个月。这是《劳动合同法》第十九条规定的。

### 2. 层层加保险

- 这可能在一定程度上或许有助于提升…… / 一般来说，通常情况下可能会……
- This could potentially help to somewhat improve… / It may possibly be the case that…

改法：一个结论最多用一个表示把握的词，放在真正拿不准的地方。

- ❌ 这个改动可能在一定程度上有助于提升加载速度。
- ✅ 这个改动应该能让首页加载快一些，我还没测。

### 3. 用“因人而异”代替回答

- 因人而异 / 视情况而定 / 取决于你的具体需求
- It depends. / It varies. / That depends on your use case.

改法：说出取决于什么，每种情况怎么办。

- ❌ 用哪个数据库，取决于你的具体需求。
- ✅ 要跨表查询、要事务，就用 Postgres；只按 key 读写、要快，就用 Redis。
- ❌ It depends on your use case.
- ✅ Use Postgres if you need joins or transactions; use Redis if you only read and write by key.

### 4. 先铺垫“这个问题很复杂”

- 这是一个复杂的问题，需要综合考虑多方面因素 / 这个问题没有标准答案
- This is a nuanced topic. / There's no one-size-fits-all answer.

改法：直接回答。真有复杂的地方，说出复杂的是哪一点。

### 5. 预先辩解

- 需要说明的是，我并不是说…… / 当然，这并不意味着…… / 我理解你可能会觉得……
- To be clear, I'm not saying… / This isn't to say X is bad. / I understand this may be frustrating.

改法：删掉。读者本来没这么想，你先替他反驳，反而把这个念头塞给了他。真有容易误解的地方，正面说清适用范围：“这条只适用于新用户。”

### 6. 不具体的提醒

- 请注意风险 / 务必谨慎操作 / 请充分测试后再上线 / 注意数据安全
- Please test thoroughly. / Use with caution. / Make sure to back up your data.

改法：说出风险是什么、在哪一步、怎么做。

- ❌ 请谨慎操作，注意数据安全。
- ✅ 这条命令会删掉整个 `data/` 目录，不能撤销。先运行 `cp -r data data.bak` 备份。
- ❌ Use with caution.
- ✅ This migration drops the `legacy_orders` table. Back it up first: `pg_dump -t legacy_orders mydb > legacy_orders.sql`.

### 7. 多余的道歉和自贬

- 非常抱歉给您带来困扰 / 我可能理解有误 / 我的能力有限，无法保证……
- I apologize for any confusion. / I may be wrong, but… / I can't guarantee…

改法：没做错就不道歉。做错了，道歉一次，说清错在哪、改成了什么。真有拿不准的理解，不要笼统地说“我可能理解有误”，说出是哪一点拿不准，问用户。

### 8. 把确认过的事说成不确定

- 测试跑过了，还写“理论上应该能过” / 日志看过了，还写“问题似乎可能出在……”
- “This should work” after it ran. / “It seems the issue might be…” after you found it.

改法：确认过就直接说，并说怎么确认的。

- ❌ 修改后应该可以正常登录了。
- ✅ 我在本地跑了 `npm test`，132 个用例全部通过。

### 9. 两边都说，不给结论

- 用户问“选哪个”，回答“各有优劣，关键看你的需求”。
- “Both have their pros and cons.”

改法：给出你的建议和理由，再说什么情况下该选另一个。

### 10. 结尾留后路

- 如有任何疑问，欢迎随时联系 / 以上仅为个人观点 / 希望对你有帮助
- Let me know if you have any questions. / Hope this helps! / Feel free to reach out.

改法：说完就停。有具体的下一步，就写下一步：“要我把完整测试也跑一遍吗？”要向读者问一个信息才能答得更准，也直接问，比如“你用的是哪个版本？”。这些都不算留后路。

## 另外几种

- **自我保证**：“我已尽力确保内容准确”“已完整保留原意”。删掉。读者没法核对这句话，它只是在替你担保。
- **知识截止声明**：“我的知识截止到某年某月，信息可能不是最新的”。删掉。真有时效问题，写明数据是哪天的、哪里能查到最新的。
- **安抚**：“完全不用担心”“这很正常”。删掉，或者换成具体判断：“这个报错不影响数据，可以忽略。”
- **列出所有边缘情况**：只写会改变读者做法的那几种。
- **同一条限制反复说**：写一次，放在读者用得上的位置。

## 要留下的

去掉防御性的话，不等于把话说满。下面这些要留：

- **真正的不确定。** 说清哪里不确定、为什么、怎么确认，放在那个结论旁边，只说一次。
  - ❌ 性能可能有一定提升，具体效果可能因环境而异。
  - ✅ 导出从 120 秒降到 40 秒。这是在我的笔记本上测的，服务器上还没测。
- **具体、要紧的风险。** 会删数据、不能撤销、涉及钱、健康、安全或法律后果的，点名风险和做法。一份回答里这样的提醒通常只有一两条；条条都写“务必注意”，读者反而一条也不看。
- **没做、没验证的部分。** 汇报里的“Safari 没测”“这次没改手机端”是读者要用的信息，要写。这和“声明自己并不是要说什么”是两回事。
- **原文和用户的把握程度。** “可能”“计划”“初步”照留。去掉的是你自己加的保险，不是原文的“可能”。
- **规定要写的声明。** 法规、平台或公司要求必须写的风险提示，以及用户要求加的声明，照写，但不要自己发明。
- **一句礼貌。** 对外通知里一句“给您带来不便，抱歉”可以有，叠三层才是问题。

## 把握程度分三档

| 你掌握的情况 | 怎么写 |
| --- | --- |
| 亲自确认过：跑过、看过、查到原文 | 直接说，加上怎么确认的 |
| 根据线索推出来的 | “我推测……，因为……” |
| 不知道、没查到 | 直说不知道，再说怎么查 |

两种极端都不对：句句加“可能”，读者分不出哪句真的不确定；句句不加，就把推测说成了事实。

## 几种常见场景

**健康、法律、理财问题。** 先给具体信息：数字、条件、步骤。再点名哪些人、哪些情况要找专业人员，什么时候找。不要用一句“请咨询专业人士”代替回答。

**做完任务后的汇报。** 第一句说结果。然后说怎么验证的。最后列出具体没验证的地方，和验证的办法。

- ❌ 已修复登录超时问题。可能还存在其他边界情况，建议上线前充分测试。
- ✅ 登录超时修好了：会话有效期从 15 分钟改成了 2 小时，改在 `config/session.py`。我在 Chrome 上登录后放了 20 分钟，没有被退出。Safari 没测；手机端走的是另一套登录接口，这次没改。

**对外通知。** 写清时间、影响什么、用户要不要做什么。不要自己加“具体时间以实际为准”“可能提前或延后”这类原文没有的说法。有联系方式就写上；没有，就不写“如有疑问请联系我们”，需要的话用【待确认：客服联系方式】标出来。

**代码注释、commit 和 PR 描述。** 不写“这可能不是最好的办法，但是……”。写为什么这么做、已知的限制是什么、什么情况下要改。

**被用户指出错误后。** 直接改好，道歉最多一次。不要接下来每句话都加“如果我理解得对的话”。
