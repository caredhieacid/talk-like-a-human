# 中文黑话、含糊说法、比喻、自造词、别扭句式和硬省略

这是例子，不是禁用词表。碰到下面的词，先问自己“我具体想说什么”，再把那个具体的东西写出来。换成另一个意思差不多的大词（“赋能”换成“助力”）不算改好。

`scripts/check_terms.py --jargon` 只会检查第一张表里的词。第二张表里的词在很多场合是正常用法，脚本不查，靠你看上下文判断。

## 基本都是黑话

这些词在它本来的专业里仍然可能是正常用法，比如控制系统里的“闭环控制”。看读者和上下文。

| 黑话 | 通常想说的是 | 改成（举例） |
| --- | --- | --- |
| 抓手 | 从哪里入手、用什么办法 | “先从退款流程改起” |
| 闭环 | 一件事从开始到结果都有人跟、有确认 | “问题修完后回访用户，确认已经解决” |
| 赋能 | 帮助、让某人能做到某事 | “让客服能自己查订单状态” |
| 打通 | 把两个系统或部门连起来 | 说清谁连谁、传什么：“订单系统会把发货状态同步给客服系统” |
| 拉通 | 把相关的人叫到一起商量 | “约产品和后端一起开会确认” |
| 拉齐 | 让大家信息一致 | “把最新方案发给所有人” |
| 对焦 | 确认重点 | “先确认这周最重要的事” |
| 沉淀 | 记录下来、整理成能复用的东西 | “写成文档”“整理成模板” |
| 落地 | 真正实施、上线、用起来 | “下周上线”“先在华东区试用” |
| 颗粒度 | 细到什么程度 | “拆到每个任务半天能做完” |
| 心智 | 用户的印象、习惯、以为的样子 | “用户以为点保存就已经提交了” |
| 底层逻辑 | 原因、原理 | “根本原因是……” |
| 顶层设计 | 整体规划 | “整体方案” |
| 打法 | 做法、策略 | “做法” |
| 组合拳 | 几个措施一起用 | 列出是哪几个措施 |
| 兜底 | 出错时的备用方案 | “接口失败时，显示上次缓存的数据” |
| 收口 | 收尾；或统一到一个入口 | 说清是哪种：“所有支付请求都走同一个接口”“这周把剩下的问题处理完” |
| 跑通 | 完整运行一遍并且成功 | “从注册到下单完整走了一遍，没有报错” |
| 反哺 | 反过来帮助另一件事 | “这些数据也能用来改进推荐” |
| 倒逼 | 迫使 | “迫使我们重新设计权限” |
| 赛道 | 领域、市场 | “这个市场” |
| 势能 | 趋势、劲头 | 直接给趋势和数据 |
| 触达 | 联系到、让用户看到 | “短信能发到 80% 的用户” |
| 卡点 | 卡住的地方 | “卡在审批这一步” |
| 痛点 | 让人头疼的问题 | 直接说问题：“用户找不到导出按钮” |
| 体系化 | 完整、有条理 | 说具体做了什么：“把散在各处的规则整理到一份文档里” |
| 对标 | 参考、和谁比 | “参考 Notion 的做法”“和竞品 X 比” |

## 看语境，常被滥用

这些词有正常意思，问题出在被拿来泛泛地用。

| 常被滥用的词 | 正常用法 | 滥用的样子 → 改法 |
| --- | --- | --- |
| 对齐 | 排版里的左对齐、内存对齐 | “我们对齐一下” → “我们确认一下理解是否一致” |
| 链路 | 网络链路、调用链（工程师之间） | “优化用户链路” → “减少用户下单要走的步骤” |
| 场景 | 具体的使用情况 | “在这个场景下” → “这种情况下” |
| 能力 | 人或系统真能做的事 | “提供导出能力” → “支持导出” |
| 价值 | 具体的好处 | “带来价值” → “每月少花两天对账” |
| 维度 | 数据分析里的维度 | “从多个维度看” → “从成本和速度两方面看” |
| 生态 | 具体的一组工具或合作方 | “完善生态” → 说出是哪些工具、哪些合作方 |
| 范式 | 学术里的范式 | “新范式” → “新做法” |
| 感知 | 心理学、传感器 | “用户感知不强” → “用户没注意到” |
| 口径 | 统计口径（数据团队之间） | “统一口径” → “统一统计规则”或“统一对外说法” |
| 水位 | 真的水位、监控里的水位线 | “资源水位偏高” → “CPU 用到了 85%” |
| 护栏 | 真的护栏 | “加护栏” → “超过 1 万元的退款需要人工审核” |
| 迭代 | 敏捷开发里的一个迭代 | “持续迭代” → “下个版本改进” |
| 复盘 | 事后回顾 | 可以用，但说清回顾什么、得出什么结论 |
| 粒度 | 锁粒度、数据粒度 | “粒度太粗” → “拆得不够细” |
| 透明 | 信息公开 | “进度透明” → “进度表所有人都能看” |
| 串联 | 电路串联 | “串联起各环节” → “把这三步连成一个流程” |
| 锚定 | 心理学里的锚定效应 | “锚定目标” → “以去年的数据为参照” |

## AI 常见的自造词

AI 很爱把一句话压成一个新词。这些词没有通用意思，只有写的人知道指什么。常见造法：

| 造法 | 例子 | 改成 |
| --- | --- | --- |
| “X 面” | 证据面、执行面、决策面、交付面 | 说清指哪些东西：“测试结果和日志”“实际要改的代码” |
| “X 层” | 语义层、意图层、治理层 | 项目里真有这一层才用，否则直接说它做什么 |
| 四字压缩 | 决策压缩、证据闭环、上下文卫生、任务持有 | 展开成一句话：“只把需要你拍板的事列出来” |
| “X 化”滥用 | 显性化、资产化、颗粒化、抓手化 | “写成明确的规则”“整理成文档” |
| “X 性”滥用 | 可感知性、可交付性 | “用户能不能注意到”“能不能交出去” |
| 英文硬翻成生词 | 上下文压力、工具面、心智负担 | 说原意：“对话太长，快超出模型一次能处理的长度” |

判断方法：在你写之前，正常中文里有人这么说吗？搜一下能找到通用解释吗？两个都不能，就展开写。

## 含糊的说法

这些词本身不是黑话，但常被拿来代替具体内容。读的人只知道“有事”，不知道是什么事。

| 含糊的说法 | 读的人会问 | 改成（举例） |
| --- | --- | --- |
| 相关问题已处理 | 哪些问题？ | “登录超时和头像上传失败这两个问题已经修好” |
| 涉及多个模块 | 哪几个？ | “要改订单、库存和通知三个模块” |
| 在一定程度上提升了效率 | 提升了多少？ | “每单处理时间从 5 分钟降到 3 分钟” |
| 进一步优化 | 优化什么，到什么程度？ | “把首页加载时间压到 2 秒以内” |
| 有效解决 / 显著改善 | 怎么算有效？ | 给结果：“上线一周，没有再收到同类投诉” |
| 从技术层面来看 | 这句话说了什么？ | 删掉，直接说技术上的原因 |
| 做了大量工作 | 做了什么？ | 列出做了哪几件事 |

说不出具体内容时，承认不知道（“还没统计”“没测过”），不要用含糊的词盖过去，也不要编一个数字。

## 比喻代替直说

比喻是为了显得会写。读的人得先把它翻译回原意，而且比喻会带进你没打算表达的意思。有直接的说法，就用直接的说法。

类比不一样。给外行解释陌生的东西时，类比能帮人理解，可以用，但要先把事情直接说清楚，再补一句“打个比方”。类比要贴切，不要让它带出不对的意思。

- ❌ 数据库迁移就像给系统做一次搬家。（只有比喻，没说迁移到底是什么）
- ✅ 新版本存数据的格式变了，现有数据要先转成新格式，这一步叫数据库迁移。打个比方，就像换新货架前，得先把货按新规则重新摆一遍。

| 比喻 | 直说 |
| --- | --- |
| 给系统装上大脑 | 系统能根据历史订单自动算出补货数量 |
| 构建数据护城河 | 积累竞争对手拿不到的用户数据 |
| 业务增长的新引擎 | 这个产品今年带来了 40% 的新用户 |
| 打造坚实的底座 | 先把账号和权限系统做稳定 |
| 这一步是整个流程的咽喉 | 这一步最容易卡住，一卡住后面都做不了 |
| 为用户保驾护航 | 说清楚防住了什么：“付款前会再核对一次收货地址” |

## 翻译腔和别扭句式

偶尔出现一个没关系，不要逐个机械替换。问题是它们堆在一起时读着别扭。

| 别扭 | 顺 |
| --- | --- |
| 对数据进行了清洗 | 清洗了数据 |
| 进行优化 / 做出调整 / 予以处理 | 优化 / 调整 / 处理 |
| 该函数用于对其参数进行校验 | 这个函数检查参数 |
| 一个用于在多个服务之间同步用户配置的轻量级后台任务 | 一个后台任务，负责在各个服务之间同步用户配置 |
| 用户权限变更审批流程优化方案 | 优化修改用户权限时的审批流程 |
| 通过引入缓存来实现性能的提升 | 加了缓存，速度快了 |
| 当用户点击按钮时，系统将会弹出提示 | 用户点按钮后，会弹出提示 |
| 这意味着我们需要重新设计 | 所以我们得重新设计 |
| 在性能方面有所提升 | 速度快了 |
| 随着业务的不断发展 | 业务变多以后 |
| 基于以上分析，我们可以得出结论…… | 所以…… |
| 作为一个开发者，你可能会…… | 你可能会…… |
| 这个问题被开发团队修复了 | 开发团队修复了这个问题 |
| 它不仅仅是一个工具，更是一种理念 | 直接说它是什么、能做什么 |
| 值得注意的是，…… | 直接说那件事 |
| 让我们深入了解一下 | 删掉，直接开始讲 |
| 这是一个很好的问题 | 删掉，直接回答 |
| 这个 PR 的 scope 有点大，需要 align 一下 | 这个 PR 改动范围太大，需要先商量一下 |
| 鉴权/限流/降级需统一收口 | 鉴权、限流和降级这三件事，统一放到网关里处理 |
| 配置 → 构建 → 部署 → 验证 | 先改配置，再构建、部署，最后检查线上是否正常 |

## 为了省字硬删词

字少了，但读的人要自己补词。需要补的，就写回去。

| 硬省略 | 写完整 |
| --- | --- |
| 已修复，待确认 | 登录超时的问题我修好了，需要你在测试环境点一下确认 |
| 配置问题，非代码 | 这是配置写错了，不是代码的问题 |
| 缓存未失效，数据旧 | 因为缓存没有失效，所以页面上还是旧数据 |
| 需用户授权方可执行 | 要等你同意后才能执行 |
| 若测试通过则合并 | 如果测试通过，就合并 |
| 改动已推，CI 绿，可合 | 改动已经推上去了，CI 全部通过，可以合并 |
| 仅影响新用户，老用户无感 | 只影响新用户，老用户不会注意到变化 |
| 原因：权限。方案：加白名单。风险：低。 | 原因是这个账号没有权限。我把它加进了白名单，影响范围很小 |
| 前改已完，后改中 | 前端已经改完了，后端还在改 |
