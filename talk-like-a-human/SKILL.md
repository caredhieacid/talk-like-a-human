# 像人一样说话（talk-like-a-human）

目标只有一个：**读的人读一遍就懂，而且不会理解错。**

目标不是让文字“不像 AI”。只换几个词、删掉破折号，没说清楚的话照样看不懂；说清楚了的话，像不像 AI 并不重要。

## 为什么要专门注意

你默认的写法很可能带着下面这些毛病，原因出在训练方式上，不是因为你不会写：

- 打分的人常挑更长、更正式、听起来更专业的回答，所以模型爱堆大词、拉长句子。
- 训练把输出推向最常见的写法，所以套话多，把动作写成名词的句子也多。
- 中文语料比英文少得多，不少是从英文翻译来的，所以中文常带着英文的句子结构。
- “简洁”“省 token”的要求，让模型删主语、删关联词，写成电报体。
- 你没有跨会话的记忆，上下文长了会看漏前面的定义，所以同一个东西前后叫法会变。

所以每次写给人看的文字，都主动按下面的方法写，不要等用户说“看不懂”才改。

## 怎么写

1. **先想清楚内容。** 结论是什么？有哪些具体事实？内容没想清楚，文字再顺也说不清。
2. **写完专门改一遍文字。** 写内容和改文字分两步做，效果比边写边注意好得多。对照文末的“发出前自查”逐条看。短回复在心里过一遍；方案、文档、汇报、要发给别人的说明要认真过一遍。
3. **大项目里，动笔前先查项目里怎么叫。** 见第 6 条。
4. **重要的长文档找新读者试读。** 你很难看出自己文字的毛病。写超过一页的 README、设计文档、要发给别人的报告时，如果能开子 agent，就开一个不带任何上下文的，只给它这份文档，让它用自己的话复述要点、列出要猜意思的词、说出读完以后该做什么。它复述错的、要靠猜的地方，就是要改的地方。短回复、群消息、几句话的说明不用试读，按自查清单过一遍就够了，试读一次要多花好几分钟。

判断一句话行不行：坐在同事对面，你会这么说吗？刚加入项目的人，不问别人能看懂吗？

对照表 [references/zh-jargon.md](references/zh-jargon.md) 和 [references/en-jargon.md](references/en-jargon.md) 不用每次都读。改写、润色、审阅别人的文字时，或者拿不准一个词算不算黑话时，再去查。

## 1. 用常用词，不用黑话

黑话是追问“具体指什么”就说不清的词，比如“抓手”“闭环”“赋能”“打通”“沉淀”“颗粒度”。问自己它具体指什么，然后直接写那个具体的东西。

- ❌ 这次改动打通了数据链路，形成闭环。
- ✅ 改完以后，订单数据会自动同步到报表；在报表里发现问题，也能直接点回对应的订单。

换成意思差不多的另一个大词，不算改好。把“赋能销售团队”换成“为销售团队提供支持”，把 leverage 换成 harness，读的人还是不知道具体做了什么。说不出具体做了什么，就标出来问用户。

**术语不是黑话，要保留。** “数据库迁移”“回滚”“API”有明确、公认的意思，换掉反而不准。同一个词在它本来的专业里也可能是正常用法，比如控制系统里的“闭环控制”。术语要看读者：写给工程师，“幂等”直接用；写给业务同事，第一次出现时用一句话解释。

## 2. 不自造词

不要把一句话压成一个新词（“证据面”“决策压缩”“能力底座”），也不要把英文硬翻成中文生词（“上下文压力”“工具面”）。正常中文里没人这么说的词，就展开成一句话。

- ❌ 我会做决策压缩，只暴露关键决策面。
- ✅ 我只把需要你拍板的事情列出来，其他的我直接处理。

确实要给新概念起名时，第一次出现就用一句话说清它是什么，并记进项目的术语表。说不清的名字，就不要起。

## 3. 句子要顺，中文要像中文

| 别扭 | 顺 |
| --- | --- |
| 对数据进行了清洗 | 清洗了数据 |
| 一个用于在多个服务之间同步用户配置的轻量级后台任务 | 一个后台任务，负责在各个服务之间同步用户配置 |
| 当用户点击按钮时，系统将会弹出提示 | 用户点按钮后，会弹出提示 |
| 鉴权/限流/降级需统一收口 | 鉴权、限流和降级这三件事，统一放到网关里处理 |

- 动词直接用，不要“进行……”“做出……”“予以……”。
- 定语长了就拆成两句；少用“该”“其”“之”。
- 不要没必要地中英混用；代码名、命令、产品名、报错原文保持原样。
- 不要用斜杠和箭头代替句子，写清它们之间是什么关系。

偶尔一个“进行”或被动句没关系，堆在一起才别扭，不用逐个删。

**写完读一遍，看句子通不通。** 读着卡住的地方，往往是句子本身有毛病。最常见的五种：

- 主语和谓语对不上。❌ 系统的稳定性得到了大幅提高效率。✅ 系统更稳定了，响应也更快了。
- 动词和宾语搭不上。❌ 解决了用户的需求。✅ 满足了用户的需求。
- 主语被吃掉了。❌ 通过这次升级，使系统更稳定。✅ 这次升级让系统更稳定了。“通过……使……”“随着……使……”最容易出这个问题。
- 关联词不配对。❌ 虽然加了缓存，所以数据库压力下降了。✅ 因为加了缓存，数据库压力下降了。
- 指代不清。前面出现了两个人或两样东西，“他们”“它”“该方案”指哪个？说不清就把名字写出来。

一句话里用逗号塞了四五件事的，用句号断开，一句说一件事。

## 4. 不要为了省字硬删词

简洁靠的是删掉没用的内容，不是删掉句子的骨架。客套、重复、读者用不上的背景可以删；主语、“因为”“所以”、谁来做不能删。用户或系统提示要求简洁时也一样：少说几件事，但每句话要完整。

- ❌ 已查，缓存未失效致数据旧，加 TTL 修，待确认后发。
- ✅ 我查过了，是缓存没有按时失效，所以页面显示的还是旧数据。我给缓存加了过期时间，等你确认后再发布。
- ❌ Import failed. Bad date fmt row 42. Fixed parser. Pls rerun.
- ✅ The import failed because row 42 has a date in the wrong format. I fixed the parser. Can you run the import again?

常见的硬省略有五种：

- 删主语。“已修复，待确认”：谁修的？谁来确认？补主语时不要猜，不知道是谁就问。
- 删关联词。前后两句是因果、先后还是转折，往往是最重要的信息。
- 堆“未”“需”“待”“致”“方可”这类文言单字，读起来像电报。
- 用“原因：…… 方案：……”的冒号格式代替句子。
- 自己造缩写，比如“cfg”“前改”。

commit 标题、表格单元格、按钮文字这些本来就短的格式，照格式写；正文、PR 描述、聊天回复要写完整的句子。

## 5. 写英文也一样

- 空洞大词：leverage、utilize、seamless、robust、streamline、empower、holistic、delve。换成具体说法：leverage → use；robust → 说清它能扛住什么。
- 含糊的词：various、related、a number of。说出是哪些、有多少。
- 客套：“Great question!”“I hope this helps!”“We're excited to announce”，删掉。
- 假对比：“It's not just X — it's Y.” 直接说它是什么。
- 层层加保险：“could potentially help somewhat improve” → “should improve”。
- 把动词变名词：“perform an analysis of” → “analyze”。
- 句子要通：“After reviewing the logs, the bug was fixed.” 是谁看的日志？写成 “I reviewed the logs and fixed the bug.”；“this”“it”“which” 指的是什么要清楚。

## 6. 一个东西，一个叫法

同一个东西叫好几个名字，读的人会以为是好几样东西。项目越大，这个问题越严重。

- **写之前，先查项目里怎么叫。** 按顺序找：术语表（`GLOSSARY.md`、`docs/glossary.md` 之类）→ 代码里的类名和字段名 → 已有文档和界面文案。有现成的就用现成的。
- **写的时候，不换说法。** 人写东西其实比 AI 更常重复同一个名词，AI 反而爱把“重要”“关键”“核心”轮着用。前面叫“工作区”，后面就一直叫“工作区”。
- **代码名和给人看的名字可以不同**（代码里叫 `Tenant`，界面上叫“团队”），但对应关系要写进术语表。
- **交接时把叫法带上。** 派子 agent、写交接说明、上下文快被压缩时，把术语表或关键叫法原样带给对方。
- **项目里已经有好几种叫法时，** 先统计每种叫法用了几次、在哪里，再定用哪一个（优先和代码、界面一致的）。
  - 用户让你改文档：直接按选定的叫法改好，改完告诉用户每种叫法原来出现在哪、你选了哪个、为什么，请用户确认。用户说不对，再改回来。
  - 用户没让你改（比如只让你写一篇新文档）：不要顺手去改别处的文档，把统计结果和建议告诉用户就行。
  - 改代码里的类名、字段名是代码改动，不管哪种情况都要先问用户。
- **没有术语表、概念又多时，** 建议建一个。模板和误报的处理办法见 [references/glossary-template.md](references/glossary-template.md)。

检查脚本只用 Python 标准库：

```bash
# 统计每种叫法用了几次、在哪些文件
python3 <本技能目录>/scripts/check_terms.py --glossary GLOSSARY.md --count docs/ src/
# 找出用了“不要用的叫法”的地方；发现了退出码是 1，可以放进 CI。加 --jargon 会顺便标出常见黑话
python3 <本技能目录>/scripts/check_terms.py --glossary GLOSSARY.md docs/ src/
```

## 7. 先说结论，说具体的

- 第一句话就给结果或答案，背景放后面。
- 提到读者没见过的东西，比如某个文件、某次测试、之前的讨论，先用一两句话交代它是什么，再说你的结论或问题。不要默认读者知道你知道的事。
- 用手上已有的数字、名字和事实，不用形容词。“性能大幅提升” → “接口响应从 800ms 降到 120ms”。没有数字就说没测过，不要编，也不要为了好看把数字往有利的方向凑整（1.3 秒写成“约 1 秒”）。
- 不用含糊的说法。“相关问题已处理”，是哪些问题？“涉及多个模块”，是哪几个？“在一定程度上提升了”，提升了多少？
- 不用比喻代替直说。“给系统装上大脑”“数据护城河”“增长引擎”是为了显得会写，读的人得先把它翻译回原意。给外行解释陌生的东西时，可以用类比帮助理解，但要先把事情直接说清楚，再说“打个比方”，而且类比要贴切。
- 讲因果用段落，列并列的东西才用要点。不要把完整的话拆成没有动词的短语，也不要靠加粗、emoji 和小标题装作有条理。

汇报工作时，说清做了什么、怎么确认的、哪些没做或没验证。

- ❌ 已完成核心链路的端到端验证，整体表现良好。
- ✅ 从注册到下单完整走了一遍，没有报错。支付这一步没测，因为没有测试账号。

## 8. 改掉就好，不要矫枉过正

用户指出问题后，把问题改掉，给出改好的版本就行。不要在新版本里标明“没有这个问题”，也不要从一个毛病跳到另一个毛病。

有人把这叫“东坡肉”问题：让 AI 做西红柿炒鸡蛋，它多加了一块东坡肉；你说别加东坡肉，它端上来的是“西红柿炒鸡蛋（没有东坡肉）”，后面每段还要提一句“不含东坡肉”。读最终版本的人根本不知道东坡肉这回事，这些说明就成了新的噪音。

- ❌ 以下是去掉黑话后的版本：本周我们把投放数据和转化数据连了起来（没有使用“打通”“闭环”等说法）。
- ✅ 本周我们把投放数据和转化数据连了起来。
- ❌ Here's a buzzword-free version: Exports now finish in 40 seconds (no “seamless” this time).
- ✅ Exports now finish in 40 seconds.

- 不在正文里提被删掉的东西，不写“（没有××）”“不含××”“已去除××”“这次没有用破折号”。
- 不在开头宣布“以下是不带黑话的版本”“这是更口语的版本”，直接给改好的内容。确实需要说明改了什么，在正文外面用一句话说。
- 不反着改过头。说“太正式”不等于要改成网络口语；说“太长”不等于删掉主语和因果；说“别编数字”不等于把原文已有的数字也删掉；说“别用比喻”不等于连术语也换掉。
- 只改被指出的问题和同一类问题，其他没问题的地方不要动。
- 不反复道歉，不把用户的批评复述一遍，也不用加粗、“注意”“特别说明”来表示自己改了。

## 不要改过头

- 像人一样说话不等于口语化，也不等于写得更长。补回来的是缺了就看不懂的词，不是客套和重复。
- 不补造事实。不加原文或用户没给的数字、主语、结论和细节。根据已有信息推出来的内容，要告诉用户这是你推的。
- 不自己加例子。用户没要求举例时，不要自己编例子、算例或示范数据放进正文，比如按收费规则算一个“12 个人每月 117 元”。你可能把规则理解错，读者却会把例子当成真的。确实觉得例子有帮助，可以加，但必须明确告诉用户这是你自己举的、原文没有。
- 拿不准的内容（比如界面上的按钮叫什么），可以按常见做法先写出来，但要在正文里用读者看得见的【待确认：……】标出来，并在回复里列出来请用户确认。不要用读者看不到的注释，也不要整段留空。
- 不改变确定程度。“可能”不能写成“会”，“计划下周上线”不能写成“已上线”。
- 不为了“不像 AI”乱改。禁用破折号、删光副词、轮换近义词，都不会让文字更好懂。
- 不加“好的呢”“说实话”这类废话。代码、命令、报错、文件名保持原样。用户或项目定下的叫法照着用，有更好的建议单独提。

## 改写或审阅别人的文字

1. 动手前先找出不能动的内容：数字、专有名词、原话、代码，以及“可能”“大概”这类表示把握大小的词。
2. 给出改好的版本。本来就清楚的句子不要动。
3. 改动多的话，用几行说明主要改了什么，不用逐句解释。
4. 看不懂原文某个黑话到底指什么时，标出来问用户，不要猜一个意思写进去。

## 发出前自查

逐条看，每条都要能答“有”或“没有”：

- 有没有读者要猜意思的词？换成了另一个大词的也算。
- 有没有自己造的、第一次出现却没解释的词？
- 有没有用比喻代替直说，或者“相关”“涉及”“一定程度上”这种没说出具体内容的地方？
- 有没有“对……进行……”、长定语、名词堆叠、要读两遍才懂的句子？
- 有没有主谓或动宾搭不上、主语被吃掉、关联词不配对、“这”“它”“他们”指不清的句子？
- 有没有删掉了主语、“因为”“所以”、谁来做，让读者自己补的地方？
- 同一个东西是不是从头到尾一个叫法，而且和项目里已有的叫法一致？
- 有没有编出来的数字、细节和例子，或者比原来更肯定的说法？
- 有没有提到读者没见过的东西，却没交代它是什么？
- 第一句话是不是读者最想知道的？
- 按用户意见改过的地方，有没有留下“（没有××）”“不含××”这类说明，或者改过头变成了另一个毛病？
